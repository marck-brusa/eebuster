# Use-case test report

Requirements for running the scenario library as a documented test run and producing a
report per run. Status: implemented in 1.0.0-rc14; section 13 lists what is not. Read together with
`02-requirements.md` (what the tool is and is not), `03-control-plane.md` (routes and
dashboard) and `20-use-case-matrix.md` (scenario format and step verbs).

## 1. Purpose

A **run** executes a chosen set of test cases against one device and produces a report that
a reader who was not present can act on: which device and vehicle were tested, with which
testbench and library versions, under which conditions, against which criteria, and the
verdict of every test case with its evidence. The headline is one sentence:

```
20 test cases: 19 passed, 1 failed, 0 skipped.
```

The report is a **use-case test report**, not a certificate. The tool checks what is
observable on the wire and through readback; it does not see the device's internal state.
Every report carries that sentence in its footer.

Readers: the engineer who ran it, a colleague reviewing it later, a device vendor, a
customer. The report must stand on its own as a single file, including when printed.

## 2. Terms

| Term | Meaning |
| --- | --- |
| Test case | One scenario YAML file. The id is the file stem (`lpc-basic-limit`) |
| Criterion | What the test case checks, stated by `covers`, with the specification reference in `spec` |
| Run | One execution of an ordered set of test cases against one peer, with a run id |
| Verdict | `passed`, `failed` or `skipped`, plus a `reason` on `skipped` |
| Evidence | The requests, responses, events and trace window a verdict was derived from |
| DUT | The device under test: the configured peer the run targets |
| Parameters | Device-specific values a test case is instantiated with (the EEBUS parameter sheet idea) |

## 3. Output formats

| Format | Role | Rules |
| --- | --- | --- |
| HTML | The human report. Master format | One self-contained file: inline CSS and JS, no external fonts, scripts, images or links required to render. Opens from `file://` without network. Interactive: collapse/expand, filter by verdict and use case, text search. Print stylesheet so the browser's "Save as PDF" yields a complete, paginated document |
| JSON | The canonical record | Everything the other formats are rendered from. Carries `report_schema: 1`. The HTML embeds the exact JSON in a `<script type="application/json">` block so a report can be re-rendered or re-imported from the HTML alone |
| JUnit XML | CI | Existing writer and shape kept. Adds a `<properties>` block on `<testsuites>` with the identification fields (run id, device SKI, serial, software revision, testbench version) and `classname` = use case on each `<testcase>` |
| CSV | Spreadsheets without a library | Two files or two sections: one row per test case, one row per step. UTF-8, header row, RFC 4180 quoting |
| XLSX | Spreadsheet users | Workbook with sheets Summary, Device, Test cases, Steps, Conformance, written with the standard library (no new dependency). Second stage: fill the "Report" worksheet of the official EEBUS parameter sheet for LPC/LPP/MPC/MGCP, keyed by ATC id |
| PDF | Printing and sending | Not generated by the tool. The HTML print stylesheet is the PDF. Reason: single binary, no child processes, no second layout engine to keep in sync |

Print stylesheet requirements: every collapsed section expands, filters reset, page breaks
before each use case, running header with run id and device serial, running footer with page
number and the "not a certificate" sentence, A4 and Letter both readable, no colour-only
meaning (verdict is also a word).

Size: a run of the full library with step evidence is in the order of hundreds of kilobytes.
Hard cap 16 MB per file. Raw frames are not embedded by default; `include_frames` embeds the
frames of the run window, bounded to 5 MB, after which the report says how many were dropped.

## 4. Report content

### 4.1 Identification

Every field names where it comes from. Fields marked **new** need data the tool does not
expose today.

**A. Report**

| Field | Source |
| --- | --- |
| Run id | `<UTC timestamp>-<4 hex>`, e.g. `20260109T101500Z-3f9a` |
| Started, finished, duration | Runner clock, UTC and local |
| Headline | Computed, see 4.2 |
| Tester, notes | Free text from the request or CLI, optional, **new** |
| Testbench version | `GET /api/v1/version` |
| eebus-go, ship-go, spine-go revisions | `runtime/debug.ReadBuildInfo()`, **new**, exposed on `/api/v1/version` as `modules` |
| Host name, OS, architecture | `os.Hostname`, `runtime.GOOS/GOARCH`, **new** |
| Scenario library | Directory, file count, SHA-256 over the sorted file contents, **new**. Two runs with the same hash ran the same criteria |
| Parameters | The resolved `parameters:` values and whether defaults were derived, see 6.4 |

**B. Testbench identity**

| Field | Source |
| --- | --- |
| Own SKI, SHIP id | `GET /api/v1/identity`, mDNS announcement |
| Announced addresses, interface | `GET /api/v1/diagnostics/network` |
| API bind and port | Config |
| Configured peer entry used | `peers[]` entry: name, label, trust mode |
| Simulator | Enabled or not, which simulated devices |

**C. Device under test**

| Field | Source |
| --- | --- |
| SKI, SHIP id, device address, device type, feature set | `GET /api/v1/peers` entry and `GET /api/v1/peers/{ski}/profile` |
| mDNS host, port, addresses | `GET /api/v1/peers/visible` entry for the same SKI |
| Brand, model, vendor, device name, device code, serial, software revision, hardware revision | Node management manufacturer data in the profile |
| EVSE manufacturer data and operating state | `GET /api/v1/evsecc/{ski}` when EVSECC is advertised |
| Entities | Address and type of every entity |
| Advertised use cases | Name, acronym, actor, version, scenario numbers, entity, from `GET /api/v1/peers/{ski}/usecases` |
| Connection | Connected and trusted flags, connected since, **new** for "since" |

**D. Vehicles**

One block per EV entity in the energy snapshot (`ev.vehicles[]`), captured at run start and
again at run end:

| Field | Source |
| --- | --- |
| Entity address | Snapshot |
| Identifications | EVCC scenario 4, every type and value |
| Manufacturer | EVCC scenario 5: brand, device name, device code, serial, software and hardware revision |
| Communication standard, asymmetric charging support | EVCC scenarios 2 and 3 |
| Charging power limits | EVCC scenario 6 |
| Connected, charging, sleep mode, phases connected | Snapshot |
| State of charge | EVSOC scenario 1 |

A vehicle present at start and absent at end, or vice versa, is reported in the conditions
section and flagged on every test case that ran after the change.

**E. Conditions**

Captured at start and end: charging session active (`ev.charging_count > 0`), consumption
power, active limits, heartbeat states (ours and the device's), trace frame count,
conformance error and warning counts, event ring sequence number. The report shows the deltas.

### 4.2 Summary

- Headline sentence with totals. `skipped` is broken down by reason.
- Per use case: advertised or not, scenarios advertised, test cases run, passed, failed,
  skipped. Use cases the library has tests for but the device does not advertise appear with
  "not advertised" so the reader sees what was not tested.
- Per risk class: read-only, live-control, disruptive, long-running.
- Run-level checks (section 6.6) with their own verdicts.
- Conditions that changed during the run.

### 4.3 Per test case

Id, name, use case, spec references (document, version, section, scenario, requirement ids,
test case id when a High-Level TestSpec defines one), criterion (`covers`), goal, hint, risk,
verification class, order in the run, started, duration, verdict, reason, failure detail.
Grouped by use case in the order the catalog lists them.

### 4.4 Per step

| Step | Evidence recorded |
| --- | --- |
| `wait_connected`, `sleep` | Elapsed time |
| `put`, `post`, `delete`, `call` | Path, the body as sent after template and parameter resolution, HTTP status, response body truncated to 4 KiB |
| `assert` | Path, HTTP status, and for every compared key: the comparison, expected value, actual value, result |
| `expect_event` | The matching event record, or the events seen in the window when none matched |
| `log` | The text |

Every step also records the trace sequence range (`first_seq`, `last_seq`) it spanned, the
conformance findings inside that range, and the use-case events inside that range. The HTML
links a sequence number to the Message trace page when the report is viewed from the
dashboard, and shows it as text otherwise.

### 4.5 Wire conformance

Conformance findings over the whole run: counts by rule and severity with the spec reference,
and the first occurrence of each rule. Taken from `GET /api/v1/trace/summary` and the trace
entries of the run window.

### 4.6 Appendix

The resolved YAML of every test case that ran, the parameters, a glossary of verdicts and
reasons, and the embedded JSON.

### 4.7 Privacy

A report contains identifiers: SKIs, serial numbers, addresses, vehicle identifications. It
never contains private keys, certificates, passwords or tokens. Reports are written under the
data directory, which is never committed; `.gitignore` gets `/data/reports/`. The README's
hygiene note mentions reports.

## 5. Verdicts

The three statuses of the scenario result stay as they are; existing consumers depend on
them. `skipped` gains a `reason`:

| Reason | When |
| --- | --- |
| `use_case_not_advertised` | The peer does not advertise a use case the test requires (existing behaviour) |
| `scenario_not_advertised` | The use case is advertised, the scenario the test is bound to is optional for the DUT actor and not advertised |
| `capability_missing` | The active stack lacks a capability (existing behaviour) |
| `phases_not_declared` | OPEV per-phase requirement not met (existing behaviour) |
| `precondition_not_met` | A stated precondition is absent: no vehicle, no charging session |
| `not_verifiable_on_wire` | The expected result needs the device's internal state and no probe is configured |
| `not_run` | The run was cancelled or aborted before this test case |

Rules:

- A scenario that the UC TS marks mandatory for the DUT actor, on a use case the DUT
  advertises, that the DUT does not advertise, fails that use case's
  `*-scenarios-advertised` test case, with the table reference in the detail. That is a
  finding, not a skip. The test cases of that scenario still run: the device has to implement
  it, and whether the data is there is what they find out.
- Optional and recommended scenarios not advertised are `skipped/scenario_not_advertised` and
  do not count against the device.
- `skipped` never contributes to "failed" in the headline. The headline counts test cases, not
  steps.
- A connection loss during a test case fails that test case with reason text "peer
  disconnected"; the remaining test cases are `skipped/not_run` and the run status is
  `aborted`.

## 6. Execution model

### 6.1 Runs

- One run at a time per process. A second request answers `409 run_in_progress` with the
  active run id.
- A run has `status`: `running`, `passed`, `failed`, `aborted`, `cancelled`.
- Runs are persisted as JSON under `<data-dir>/reports/<run-id>.json` as soon as they start and
  rewritten on every test case completion, so a crash leaves a readable partial report. The
  other formats are rendered on demand from the JSON, never stored. Rendering changes never
  require a rerun.
- The existing synchronous `POST /scenarios/{name}/run` and `POST /scenarios/run-all` keep
  their shape and behaviour and additionally create a persisted run, returning its `run_id` as
  an added field.

### 6.2 Selection and order

Selection: all, read-only only, by use case acronym, by risk, by explicit id list, with
`include_long_running` default false. Order within a run is fixed: `smoke-pairing`,
`device-profile-discovery`, then by use case in catalog order, within a use case read-only
before live-control before disruptive, then by id. Test cases with `cleanup: true` run last,
always, even after a failure or cancellation, and are reported in their own group. The order
is part of the JSON so two reports can be compared line by line.

### 6.3 Preconditions

Sections 4.1 C to E are captured before the first test case and after the last. A test case
whose `requires` names a vehicle or a charging session is `skipped/precondition_not_met` when
the start capture lacks it, with the detail saying what was missing.

### 6.4 Parameters

Device-specific values live in `eebus.yaml` under the peer:

```yaml
peers:
  - name: device-under-test
    ski: 0123456789abcdef0123456789abcdef01234567
    parameters:
      nominal_max_w: 11000
      limits_w: [11000, 5500, 4200, 4237, 0]      # APCL_01..05 of the LPC parameter sheet
      failsafe_w: [4200, 2000, 0]                  # FCAPL
      limit_durations: [PT2H, PT15M, PT1M]         # APCL_DUR
      failsafe_durations: [PT1H54M, PT2H, PT24H]   # FCAPL_DUR
      production_nominal_max_w: 0                  # LPP, 0 = not applicable
```

Scenarios reference them as `{params.limits_w.1}`, resolved by the same lookup as
`{peer.ski}`. When a value is absent the runner derives it from the device's announced
nominal maximum (`GET /lpc/{ski}/nominal-max`) with fixed ratios and records "derived" in
the report. A test case that needs a parameter neither configured nor derivable is
`skipped/precondition_not_met`.

### 6.5 Long-running test cases

`long_running: true` marks test cases that wait on specification timers (60 s, 90 s, 120 s
steps in the LPC and MPC test specifications). They run only when selected explicitly or
with `include_long_running`. The runner's HTTP client timeout applies per request; `sleep`
steps are not subject to it. Progress is published while they wait.

### 6.6 Run-level checks

Computed by the runner over the whole run, reported next to the test cases:

| Check | Verdict rule |
| --- | --- |
| Wire conformance | No conformance finding of severity error in the run window |
| Connection stability | Peer stayed connected from first to last test case |
| Vehicle stability | Same vehicle entities and identifications at start and end, when a vehicle was present |
| Device heartbeat | For LPC/LPP: the device's heartbeat kept arriving throughout, gaps shorter than its announced timeout |

### 6.7 Progress and cancellation

Progress is published on the event bus, level `lifecycle`, events `run_started`,
`run_progress` (index, total, test case id, verdict so far), `run_finished`,
`run_cancelled`, with the run id in `data`. `POST /runs/{id}/cancel` stops after the current
step, runs the cleanup group, and marks the rest `not_run`.

### 6.8 Determinism

Same scenario library hash, same parameters, same device: same test cases in the same order
with the same criteria. The report says when it is not comparable to another (different hash,
different parameters, different firmware).

## 7. Scenario metadata

New optional keys on a scenario file. All are optional; files without them keep working.

```yaml
spec:
  use_case: LPC                           # acronym from the use-case catalog
  scenario: 2                             # UC TS scenario number the test is bound to
  document: "EEBus UC TS Limitation of Power Consumption V1.0.0"
  section: "3.4.2"
  requirements: [LPC-TS-016, LPC-TS-038]  # ids as the specification writes them
  test_case: ATC_COM_PT_CSConnection_008  # only when a High-Level TestSpec defines one
  verification: readback                  # wire | readback | needs-device-probe
long_running: false
cleanup: false
```

- `verification` states how the verdict is reached: `wire` (observed on the trace or events),
  `readback` (written then read back over the use case), `needs-device-probe` (expected
  result is internal device state; `skipped/not_verifiable_on_wire` until a probe exists).
- The catalog (`GET /scenarios/catalog`) passes `spec`, `long_running` and `cleanup` through.
  The report groups by `spec.use_case` and falls back to `category`.
- The CI scenario check grows from "parses as YAML" to: known top-level keys only,
  `spec.use_case` is a catalog acronym, `spec.scenario` is within that use case's scenario
  count, `verification` is one of the three values, every `{params.*}` reference names a
  parameter the schema in 6.4 defines.
- Copyright: the specifications may not be reproduced. A scenario cites ids and paraphrases
  the criterion in one line; it never pastes a table or a paragraph.

### 8.1 REST

Added. Existing routes are unchanged.

| Route | Behaviour |
| --- | --- |
| `POST /api/v1/runs` | Body: `peer`, `selection` (`all`, `read_only`, `use_cases: []`, `risks: []`, `ids: []`), `include_long_running`, `include_frames`, `tester`, `notes`. Starts the run asynchronously. `202` with `run_id`. `409` when a run is active |
| `GET /api/v1/runs` | Newest first: id, status, started, headline, peer SKI and label |
| `GET /api/v1/runs/{id}` | The run JSON, partial while running |

| `GET /api/v1/runs/{id}/report.xlsx` | Workbook |
| `POST /api/v1/runs/{id}/cancel` | See 6.7 |

Downloads carry `Content-Disposition` with `<run-id>-<device-serial-or-ski>.<ext>`.

### 8.2 CLI

```
eebus-testbench run-all [dir] -base-url URL [-use-case LPC,MPC] [-read-only] [-ids a,b]
    [-include-long-running] [-tester NAME] [-notes TEXT]
    [-html FILE] [-json FILE] [-junit FILE] [-csv FILE] [-xlsx FILE]
eebus-testbench run <scenario.yaml> ... same output flags
eebus-testbench report <run.json> [-html FILE] [-junit FILE] [-csv FILE] [-xlsx FILE]
```

`run-all` and `run` execute the local scenario files against the instance at `-base-url`
with the same run manager the server uses, so the files are rendered by the same code; the
record stays with the CLI and is not listed under the server's runs. `report` re-renders a
stored JSON, or the JSON embedded in an HTML report, without a server. Exit code non-zero when
the run status is not `passed`.

### 8.3 Dashboard

No new page. The Test runner page gains:

- Grouping by use case with per-group counts and a per-group "Run" button; a check box per
  group and per test case; "Include long-running"; a tester name field remembered in
  `localStorage`.
- A run header: current or last run, progress from the `run_progress` events, headline,
  and a "Download" control with HTML, JSON, JUnit, CSV, XLSX.
- A list of the report files in the reports folder from `GET /runs`, read from the folder on
  every request: no index, no delete; managing reports is managing files.
- Per-row results as today, plus the reason on skipped rows and a link to the step's trace
  sequence range on the Message trace page.
- New strings in all three dictionaries; the i18n consistency check must pass. The report
  file itself is English.

## 9. Use-case requirements

The device under test plays the device-side actor of each use case; the testbench plays the
energy-manager side. Scenario tables below are the "Scenario implementation requirements for
Actors" of each UC TS (M mandatory, R recommended, O optional) for the DUT actor and for the
testbench actor. High-Level Test Specifications exist for LPC, LPP, MPC and MGCP only; their
abstract test cases (ATC) that test the energy-manager side test the testbench itself and
are out of scope. OPEV, OSCEV, EVCC, EVSECC, CEVC, EVCEM, EVSOC, VAPD, VABD and OHPCF have no
test specification; their criteria are the numbered requirements and the content tables of
the UC TS.

Every test case listed as required ships with `spec`, a one-line `covers`, a `goal`, and
where the simulator can play the device side, a run against the simulator in CI.

### 9.1 Common

Runs first, independent of use cases.

| Test case | Criterion | Status |
| --- | --- | --- |
| `smoke-pairing` | SHIP connection and SPINE setup | exists |
| `device-profile-discovery` | Entities, features, advertised use cases | exists |
| `common-manufacturer-data` | Node management manufacturer data present: at least brand or vendor, serial and software revision non-empty. Feeds the report header | required |
| `common-use-case-versions` | Every advertised use case states a version; versions the catalog does not know are listed in the detail | required |
| `conformance-window` | No conformance errors during discovery and reads | exists |

### 9.2 LPC, Limitation of Power Consumption

DUT: Controllable System. Testbench: Energy Guard. UC TS V1.0.0. High-Level TestSpec V1.0.0
with 53 ATCs, 44 of them Controllable-System side, plus the parameter sheet.

| Scenario | DUT | TB |
| --- | --- | --- |
| 1 Control active power consumption limit | M | M |
| 2 Failsafe values | M | M |
| 3 Heartbeat | M | M |
| 4 Constraints | R | M |

Exposed today: limit, failsafe, nominal maximum, heartbeat start/stop/status,
`?unchecked=true` on the failsafe write. Twenty-one test cases exist.

Specification-derived test cases:

| Test case | Criterion | Verification |
| --- | --- | --- |
| `lpc-scenarios-advertised` | Scenarios 1 to 3 advertised, mandatory for the Controllable System; scenario 4 recommended | wire |
| `lpc-limit-value-set` | Every `limits_w` value accepted and read back equal, without a duration; then the first limit with every `limit_durations` value, read back with a duration (ATC_COM_PT_CSConnection_007) | readback |
| `lpc-limit-above-maximum` | A 1 MW limit is accepted; the readback is active and lies between the nominal maximum and the value sent, since the device may cap it (ATC_COM_PT_CSConnection_006, LPC-TS-035/4) | readback |
| `lpc-negative-limit` | A negative limit and a negative failsafe limit are both rejected: neither value comes back (ATC_COM_PT_CSConnection_003) | readback |
| `lpc-failsafe-value-set` | Every `failsafe_w` value accepted and read back; every `failsafe_durations` value, within 2 h to 24 h, read back between 2 h and the value written, so a device that caps 24 h at its own maximum passes; a duration below 2 h is `lpc-failsafe-duration-range`, which bypasses the stack's range check (ATC_COM_PT_CSConnection_008) | readback |
| `lpc-heartbeat-timeout` | The device's heartbeat announces a timeout of at most 60 s (UC TS Table 26) | wire |
| `lpc-heartbeat-continuity` | Five consecutive heartbeat notifications from the device, each within 60 s of the previous one (ATC_COM_PT_CSHeartbeat_001) | wire, long-running |
| `lpc-release` | From an active limit, a deactivation leaves the limit inactive (ATC_COM_PT_CSTransition6_002) | readback |
| `lpc-failsafe-on-heartbeat-loss` | From unlimited/controlled (heartbeat running, limit deactivated), after our heartbeat stops the device falls to its failsafe power within 120 s plus margin: consumption power read over MPC is at or below the failsafe value (ATC_COM_PT_CSTransition5_001) | readback, long-running |
| `lpc-no-write-before-heartbeat` | In failsafe state, 130 s without our heartbeat, an active limit write is not evaluated and does not come back; after the heartbeat returns a deactivation is accepted (ATC_COM_PT_CSFS_001) | readback, long-running |
| `lpc-nominal-max` | Scenario 4, recommended: Power Consumption Nominal Max present and positive (LPC-TS-010/1, 010/2, 038) | readback |
| `lpc-cleanup` | Limit released, heartbeat running | `cleanup: true` |

`lpc-heartbeat-loss` was removed: it duplicated `lpc-failsafe-on-heartbeat-loss` without an
assertion. The run-time parameter `failsafe_durations` must stay within 2 h to 24 h: the stack
refuses other values before they reach the device.

State names of the test specification (`CF_CS_FS`, `CF_CS_Limited_wo_dur`) are internal
device state; test cases that can only be decided from them use
`verification: needs-device-probe`.

### 9.3 LPP, Limitation of Power Production

DUT: Controllable System. Testbench: Energy Guard. UC TS V1.0.0. High-Level TestSpec V1.0.0,
same structure as LPC, 44 Controllable-System side ATCs.

| Scenario | DUT | TB |
| --- | --- | --- |
| 1 Control active power production limit | M | M |
| 2 Failsafe values | M | M |
| 3 Heartbeat | M | M |
| 4 Constraints | R | M |

Exposed today: limit, failsafe, nominal maximum. The energy guard heartbeat is the CEM
entity's and shared with LPC: `eg-lpc/StartHeartbeat` serves both use cases, and the device
answers with one Controllable System heartbeat, so the LPC scenario 3 test cases cover LPP
scenario 3 when both use cases are advertised. The production limit is negative under the
passive sign convention (LPP-TS-001); the failsafe production limit and the nominal maximum
are magnitudes, at least zero (LPP-TS-038). Six test cases exist.

| Test case | Criterion | Verification |
| --- | --- | --- |
| `lpp-scenarios-advertised` | Scenarios 1 to 3 advertised, mandatory for the Controllable System; scenario 4 recommended | wire |
| `lpp-basic-limit` | A -1500 W production limit accepted and read back, after the heartbeat; released after (ATC_COM_PT_CSConnection_007) | readback |
| `lpp-read-current` | The production limit readable | readback |
| `lpp-failsafe` | A 2 kW failsafe production limit and a 2 h duration written and read back (ATC_COM_PT_CSConnection_008) | readback |
| `lpp-failsafe-window` | Announced failsafe limit at least 0, duration within 2 h to 24 h | readback |
| `lpp-nominal-max` | Scenario 4, recommended: Power Production Nominal Max present and positive (ATC_COM_PT_CSUnlCntrl_003) | readback |
| `lpp-cleanup` | Limit released | `cleanup: true` |

Still missing: the value-set and transition test cases with `production_limits_w`. Lower
priority than LPC: fewer devices advertise it.

### 9.4 MPC, Monitoring of Power Consumption

DUT: Monitored Unit. Testbench: Monitoring Appliance. UC TS V1.0.0. High-Level TestSpec
V1.0.0 with 56 ATCs, 20 Monitored-Unit side.

| Scenario | DUT | TB |
| --- | --- | --- |
| 1 Monitor power | M | M |
| 2 Monitor energy | O | O |
| 3 Monitor current | R | R |
| 4 Monitor voltage | O | O |
| 5 Monitor frequency | O | O |

Exposed today: `GET /mpc/{ski}`. A test case per scenario exists (`mpc-live-power`,
`mpc-scenario-2-energy` to `mpc-scenario-5-frequency`), plus the phase consistency check,
`mpc-notification` and `mpc-consumption-sign`.

One per scenario, each skipped with `scenario_not_advertised` when the scenario is optional
and absent:

| Test case | Criterion | Verification |
| --- | --- | --- |
| `mpc-scenario-1-power` | Total power present; per-phase powers sum to the total within tolerance (replaces the two existing phase tests as the scenario-1 group) | readback |
| `mpc-scenario-2-energy` | Consumed and produced energy present; a second read after 60 s is not lower | readback |
| `mpc-scenario-3-current` | One current per connected phase, plausible for ampere | readback |

## 10. Phases

## 11. Acceptance

Unit tests in Go for: the HTML renderer on a fixture run (headline present, every test case
id present, no `http://` or `https://` in `src` or `href`, size below the cap, embedded JSON
equals the input), JSON round trip through `report`, JUnit validity and properties, CSV
columns, verdict rules of section 5 including the mandatory-scenario failure, parameter
resolution and derivation, run ordering and the cleanup group running after a failure and
after a cancellation, the 409 on a concurrent run, the partial JSON after an interrupted run.

CI: the extended scenario check, the i18n check, the dashboard JavaScript parse, and a run of
the read-only selection against the simulator with the vehicle enabled that must produce a
report with zero failed test cases.

Hardware: a run against a real device is described in the pull request with the report
attached, and any test case that did not behave as on the simulator is listed.

## 12. Decisions taken

| Decision | Choice | Reason |
| --- | --- | --- |
| PDF | Browser print of the HTML | Single binary, one layout to maintain |
| Report language | English | One template; the dashboard stays trilingual |
| Statuses | Unchanged three, plus `reason` | Existing JSON consumers keep working |
| Where reports live | `<data-dir>/reports/` | Never tracked, survives restarts, one place to clean |
| Rendering | On demand from JSON | Renderer fixes apply to old runs |
| Single-test "Run" button | Creates a persisted one-test run | Every verdict has a report |
| XLSX writer | Standard library | No new vendored dependency; the workbook needs only inline strings, numbers and one header style |
| CLI runs | Local scenario files, same run manager | `run-all <dir>` keeps working against a remote instance with files it does not have |
| Device probe | Interface defined, no implementation | Device specific; the generic tool ships the hook only |
